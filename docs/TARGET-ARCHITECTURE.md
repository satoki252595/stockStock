## 1. 一文の目標像

**1つの事実は1つの場所にしか存在せず、そのすべてが「いつ時点か・何の原本から来たか・どのライセンスか」を持ち、原本 → 事実 → 投影の一方向にだけ流れる。画面・REST・MCP はその投影を同じ契約で読み、鮮度とジョブ結果を書かないジョブは成功にできず、ライセンス境界は宣言ではなく bind の有無で守られ、実行が 712 分遅れても欠損しない — 月 $5 のまま、個人一人で回り続けるデータ基盤。**

## 2. なぜ変えるのか（実測で示す5点）

### 2.1 同じ事実が複数箇所にあり、98.7% で食い違う

```
core_stock_financials × finmath_price_snapshot: n=3,759 / price 不一致 3,711 (98.7%) / per 不一致 3,372
7203: core 3,031円(09-11) / otakara 2,980円(08-10) / finmath 3,031円(09-11)
```

`otakara` の 2,980 円は 33 日前の値である。**同じサイトのどのドアから入るかで株価が変わり、どちらが正しいか誰も答えられない。** OHLCV に至っては D1 2本 + R2 2箇所の計4箇所に同じ Yahoo 由来データがある。Yahoo は TTM を随時改訂するため、取得時刻の違う複製は原理的に収束しない。

なお `finmath` が 09-11 に揃っているのは、前回調査が `/financial-math/dcf?code=7203` を開いた副作用である（読み取り経路の GET が Yahoo を叩いて D1 に書く設計）。それ以前は 3,759 行中 3,547 行（94.4%）が 2026-06 以前だった。

### 層の責務（1行ずつ）

| 層 | 責務 | やってはいけないこと |
|---|---|---|
| L0 原本 | 取得したバイト列を sha256 で不変保存 | 上書き・加工 |
| commit gate | すべての書き込みを検査する唯一の口 | ここを迂回する経路を作る |
| L1 事実 | 「測った値」を追記のみで保持 | UPDATE（訂正は新しい行 + supersedes） |
| derive | L1 → L2 の純関数 | 外部 API 呼び出し・非決定的な入力 |
| L2 投影 | 画面が読む断面 | 独立した真実を持つ・原本を持たない事実を含む |
| query contract | 意味づけされた問いだけを公開 | 公開 Worker からの生テーブル参照 |
| 読み取り面 | 読むだけ | 書く（現 004 の遅延充填） |

## 4. データモデル

### 4.1 層を接頭辞で強制する

現状最大の事故源は**断面か時系列かがスキーマから読めない**ことである。`core_stock_financials` は `data_date` と `fetched_at` を持ちながら `stock_id` 単独 UNIQUE で 1 銘柄 1 行。実測でも 3,715 行が 2026-09-11 に集中し、49 行だけが 5〜8 月の置き去り（すべて上場廃止銘柄）。「`data_date` で絞れば過去が取れる」と信じたクエリが、エラーにならず黙って 0 行または混在結果を返す。これは SQLite の二重引用符フォールバックで 3 ヶ月機能が死んだのと同じ「**エラーにならずに間違う**」類の失敗であり、型と命名で潰すしかない。

| 層 | 接頭辞 | 一意制約 | 上書き | 必須列 |
|---|---|---|---|---|
| L1 事実 | `f_` | (key, as_of) | 追記のみ | `raw_sha256` / `source` / `license_tag` / `as_of` / `fetched_at` / `quality` **すべて NOT NULL** |
| L2 投影 | `p_` | (key) のみ | 全消し再生成 | `as_of` / `source_max_date` NOT NULL。原本参照は持たない |
| 運用 | `ops_` | — | — | — |

定義関数は2つしか用意しない: `defineSeries({ key, asOf })` と `defineProjection({ key })`。**断面テーブルを手で作る手段を残さない。** 断面が要るなら `latest(series)` を derive で作る。断面を手で作れるようにすると、それが第2・第3の真実になる（実測: 株価断面 3 表、指標 3 系統）。

### 4.3 投影を1セットに統合する

| `p_indicators` | `swing_stock_indicators` + otakara の ma/rsi/macd + `rsi_percentile.operating_margin_ttm` |

補足として、`rsi_percentile.operating_margin_ttm` と `core_stock_financials.operating_margin` は **3,764 件すべて完全一致する**。同一ジョブが同時刻に書いているから一致しているだけで、片方の更新時刻がずれれば即座に食い違う。**投影の統合はこの種の「偶然の一致」への依存を消す。**

### 4.4 保存先の決定規則（課金軸で決める）

| ストア | 課金軸 | 置くもの | 置かないもの |
|---|---|---|---|
| **D1** | rows read（25B/月）・rows written（50M）・storage（5GB） | 述語で絞れる小さい断面、検索が要るメタデータ、運用表 | **全走査されうる長い時系列** |
| **R2** | GB-month（$0.015、10GB無料）・Class A/B | 大きい不変ブロブ、長い時系列の塊 | 更新頻度の高い小断面（全置換 RMW を誘発する） |
| **Notion** | API レート（実効 1.04〜1.27 req/s が律速） | 人が目で見るダイジェスト数百行 | **全件書き込み** |

**D1 に長い時系列を置かない**が本設計で最も強い制約である。根拠:

- `/financial-math/emh?type=momentum` は 1 表示で D1 を **647,630 rows read**、TTFB **0.86〜1.01 秒**。他 13 経路は 42〜195 ms なので **8〜20 倍遅い**。事前計算列なら **7,528 rows read**（85 分の 1）
- 日付条件を足しても `rows_read` は 336,170 のまま下がらない（`idx_swing_ohlcv_date` が `ORDER BY stock_id,date` に負ける）
- 逆に R2 のみで動く 007 vwap-analysis は `/api/daily` 223 KB を 76〜135 ms、`/api/intra` 496 KB を 81 ms で返している。**実測上いちばん素直に動いているのがこの形**

つまり **D1 に時系列を置くと、それを全走査する画面が必ず生える**。実装者の注意力の問題ではなく、SQL が書ける以上は書かれるという構造の問題なので、置き場所で解決する。

### 4.5 R2 キー設計（全置換 RMW を構造的に不可能にする）

```
raw/{source}/{datatype}/{yyyy}/{yyyy-mm-dd}/{scope}/{sha256}.{ext}.gz   不変・追記のみ
facts/price_daily/{code}/{yyyy}.ndjson.gz                               当年シャードだけ書く
facts/intra/{yyyy-mm-dd}/{code}.ndjson.gz                               日次シャード・追記のみ
facts/supply/{code}.json                                                 merge+後退禁止ガード（現行踏襲）
```

現状は `daily/{code}.json` / `intra/{code}.json` の**その場上書き**で、1 run あたり GET 1.90 GB + PUT 1.91 GB = 3.80 GB、月 13 run で **49.5 GB を動かして新規データは約 1%**。8,727 オブジェクト中 8,590 が 2026-09 更新 = バケット全体が毎回書き換わっている。これが vwap-ingest 中央値 52.6 分・**最大 300 分（timeout 到達）**の正体で、帯域律速なので並列度を上げても頭打ちになる。timeout に達しているということは**もう拡張余地が無い**。

あわせて `intra/` の保持を `KEEP_DAYS=365` から**提供範囲の 60 日**に合わせる（コード自身が「最大 60d まで提供する」と書いている）。

### 4.6 銘柄コード

```ts
type StockCode = string & { readonly __brand: "StockCode" };
parseStockCode(raw: string): StockCode | null   // 実装は1つだけ
```

生の `string` を受ける API を型で禁じる。現状 `to_ticker` は検証なしで `f"{code}.T"` と連結するため `' 7203 '` → `' 7203 .T'`、`'16714'` → `'16714.T'` が例外にならず、yfinance が空フレームを返すので**欠測として静かに消える**。ブランド型ならこの経路が消える。

ETF・優先株は別エンティティとして型を分ける（`jss_supply_latest` の distinct code 4,351 件中 592 件が `core_stocks` に無く大半が ETF、`core_stocks` に 4 文字契約を破る行が 6 件ある、という現状の孤児はこれで表現される）。

## 7. 非機能の目標値

**現状、許容鮮度の数値定義がどのドキュメントにも存在しない**（設計書 3 本を `鮮度|SLO|許容遅延|freshness|staleness` で grep して閾値 0 件）。定義が無いので「33 日古い」が異常かどうかを誰も判定できない。まずここを埋める。

### 7.1 鮮度

`ops_dataset_freshness` に機械可読で持ち、**UI・API・監視がすべてこの 1 表を見る**（別々に持つと片方だけ腐る）。

| データセット | 緑 | 黄 | 赤 | 実測（2026-09-12） | 判定 |
|---|---|---|---|---|---|
| 日次株価・指標 | ≤30h | –48h | >48h | **2.4h** | 緑 |
| TDnet 開示 | ≤30h | –48h | >48h | 約 11h | 緑 |
| EDINET 提出 | ≤30h | –48h | >48h | 約 11h | 緑（ただし故障時の proc=0 を現状検知できない） |
| 日証金 貸借 | ≤30h | –48h | >48h | **0.5 日** | 緑 |
| 銘柄マスタ（JPX） | ≤40日 | 40–45日 | >45日 | **33.0 日** | 緑（あと 7 日で黄） |
| 財務（四半期/年次） | 提出から ≤48h | –7日 | >7日 | D1 は **0 行** | **赤** |
| 株主優待 | ≤40日 | 40–50日 | >50日 | **81.5 日** | **赤** |
| VWAP 5分足 | ≤30h | –72h | >72h | 当日 | 緑 |
| VWAP 信用残（週次） | ≤9日 | 9–16日 | >16日 | 2026-07-03/07-10 週が恒久欠落 | `f_ingest_gaps` に `permanent` として記録 |

**加齢の測り方（2026-09-12 追記）**: 上の時間は**データ基準日**からの経過であり、日次データセットは**営業日**で数える（土日を差し引く）。収集ジョブの cron が平日のみ（`prices_daily 30 10 * * 1-5` など）なので、暦時間で当てると土曜〜月曜が必ず黄〜赤になり**週 3 日鳴る通知**になる。祝日カレンダーは持ち込まず、「1 営業日の欠落は緑〜黄、2 営業日で黄、3 営業日で赤」という設計で祝日 1 日分を吸収する。一次ソース自体に公表遅延があるデータセット（日証金の貸借残は翌営業日 11 時頃の公表で `data_date` が常に T-1）は `FreshnessSlo.lag_days` に営業日数で持たせ、「基準日 + lag」をあるべき到着時刻とする。実装と根拠は `src/jp_stock_pipeline/cloud_store/slo.py`。

**既知の赤の扱い**: `financials`（`jss_financials` 0 行）と `yutai_benefits`（81.96 日）は当面赤のままなので、`slo.ACCEPTED_RED` に**受容理由つきで**宣言し、`ops_check` は警告に落として終了コードを落とさない。理由の無い受容は「消音」と区別できないため文字列を必須にしている。受容期限は置かない（いつまで許すかは投資判断でユーザにしか決められないので、勝手な日付を置いても「期限が来たのでまた鳴る」だけになる）。代わりに**何が決まれば外せるか**を理由に書く。

**強制（2026-09-12 改訂。旧案は下記の「採らなかった案」）:** 鮮度は**収集ジョブとは別の観測ジョブ（`jobs/freshness_probe.py`）が実表を測って**記録する。収集ジョブ側は `ops_job_runs`（D1 では `jss_job_runs`）だけを書き、鮮度の自己申告はしない。**空配列を返す経路は 200 ではなく 503 にする。**

> **採らなかった案: 「鮮度と `ops_job_runs` を書かないジョブは成功にできない（ライブラリの `finally` で書き、書けなければ失敗）」**
>
> 理由は 2 つ。
>
> 1. **壊れた writer が「新鮮だ」と自己申告できる。** 実測で EDINET の日次収集は 11 営業日連続 processed=0 のまま「成功」していた。自己申告方式ではそのとき鮮度表に「今さっき更新した」が入る（実際には 1 行も増えていない）。観測ジョブが実表を測れば、writer が黙って死んでも表は嘘をつかない。
> 2. **記録層の失敗でジョブ本体の成否を左右させたくない。** `finally` で書けなければ失敗にすると、Cloudflare の一時障害や D1 トークンの失効で、収集そのものは全件成功しているジョブが赤になる。それは「本当に壊れた日」の赤と区別できず、通知の価値を下げる。だから記録は `safe_record_*`（警告 + 返り値）に留め、**「記録が止まっている」ことは観測ジョブの生存確認（`ops_check` が `jss_job_runs` の `freshness_probe` の成功を見る）で別途検知する**。
>
> トレードオフ: 観測ジョブ自体が止まれば鮮度表は凍結する。それを検知するために `ops_check` は「`freshness_probe` が `status='成功'` で 48 時間以内に走っているか」を必ず見る（`status` を絞らないと、毎日失敗していても「生きている」を返してしまう）。

### 7.2 正確性

第2ソース突合は目標に置かない（stooq 死亡。代替探索の運用コスト > 得られるもの）。代わりに**自己整合チェック**を置く。外部依存ゼロで、現に異常を検出できている。

### 7.4 成否の判定式（「一部失敗」を廃止する）

```
緑 = 必須データセットがすべて green 以内 かつ 帯域チェック後の被覆率 ≥ 97%
黄 = yellow 以内、または 3 日連続で同じ銘柄が欠損
赤 = それ以外（ガード違反・書き込み不能を含む）
```

101/3,818 = 2.6% の欠損は緑の範囲内。ただし欠損銘柄は `f_ingest_gaps` に残り、翌日のキャッチアップ対象になり、3 日続けば黄になる。**「毎日 101 件失敗しているのに緑」も「1 件失敗したから赤」も起きない。**

`cloud_failed` のような「成否に影響しないカウンタ」は廃止する（現状 `config.py:175` の `enabled() = r2_enabled() or d1_enabled()` は片系統だけの設定でも Sink を生成するため、**資格情報が欠けていると書込 0 件でも exit 0** になる）。

### 7.5 時刻に依存しない

GitHub Actions のスケジュール遅延は実測**中央値 106〜152 分、最大 712 分**。21:00 JST 起動が 00:3x〜06:3x JST にずれ、「今日」が翌日になって 11 営業日空振りした。

```
cursor = ops_ingest_cursor[dataset].last_complete_date
for d in business_days(cursor+1 .. today)[:20]:     # 上限20営業日
    if already_have(d): continue                     # 冪等
    fetch(d) → R2 L0 → f_* → advance cursor
    on failure: f_ingest_gaps へ記録して継続
```

712 分遅れても、丸 3 日止まっても、次の実行が自動で埋める。**追加費用ゼロ、実装コストほぼゼロで、11 営業日の欠損が構造的に発生しなくなる。** 本設計で最も費用対効果の高い判断。

### 7.6 どう気づくか

日次ヘルスチェック（GHA 約 30 秒 / $0）が `ops_dataset_freshness` と `ops_job_runs` を読み、黄/赤があれば **GitHub Issue を 1 本**起票（既存 open があれば更新）。異常が無ければ何も出さない。ただし**週 1 回だけ正常でも heartbeat を出す**（「静かなのが正常なのか、通知系自体が壊れているのか」を区別するため）。

外部監視 SaaS は持ち込まない。個人運用で通知チャネルを増やすと見なくなる。現状 14 workflow に通知が 0 行で、GitHub の既定メールも実際に効いていない（11 営業日と 21 run が放置された）ので、**「静かなときは静か、異常時だけ 1 つ立つ」**が唯一機能する形。

そして最大の監視は**画面そのもの**である。UI に出す `as_of` と監視が見る `as_of` を同じ 1 表にすれば、ポータルを開いた瞬間に「優待が 81.5 日古い」が目に入る。

## 8. ライセンス遵守の構造

### 8.1 現状は「気をつける」しかなく、実際に守られていない

```
kabulab-cf の personal-only|license_tag|licenseTag grep: 0 件
D1 jss_column_license (7行) と worker/src/shared/license.ts の RESTRICTED_COLUMNS = 2つの別実体。
  どちらも照合コードが本番の公開面に 0 行
jss_column_license が宣言する edinet_code / sector33 / sector17 / instrument_type は
  core_stocks 3,818 行すべて NULL = 「まだ存在しない列」を記述している
```

### 8.2 4 層で守る（上ほど強い）

| 層 | 仕組み | 破れるか |
|---|---|---|
| **第0層: bind** | 公開 Worker に personal-only を含む D1 表と R2 バケットを**そもそも bind しない** | コードにバグがあっても物理的に到達できない |
| **第1層: ビュー** | 公開 Worker が読むのは列単位ライセンス地図から**生成された公開投影ビュー**だけ。制限列はビューに存在しない | SQL を書いても列が無い |
| **第2層: 型** | 同じ地図から TS 型を生成。公開面のレンダラは `PublicSafe<T>` しか受け取れない。降格には明示的な `redactFor()` 呼び出しが要る（grep 可能・レビュー可能） | コンパイルエラー |
| **第3層: CI** | 公開 Worker のバンドル成果物に制限列名が文字列として現れたら落とす。本番レスポンスを走査する E2E も置く | grep 1 行 |

**地図は 1 つだけ。** 契約ファイルに置き、そこから D1 のビュー定義・`jss_column_license` の中身・TS 型・MCP スキーマをすべて生成する。現状の「2 つの真実が乖離しても誰も検知しない」状態を構造的に消す。

### 8.3 タグを 4 つにする

| タグ | ソース | 公開面 | 私用面 | 備考 |
|---|---|---|---|---|
| `commercial-ok` | EDINET | ○ | ○ | 財務・銘柄コード・社名 |
| `factual-cite` | TDnet | ○（事実のみ: いつ・誰が・何を） | ○ | 原本本文は出さない |
| `personal-only` | JPX / 日証金 / Yahoo | **×** | ○（私的利用） | 価格・業種・市場区分・需給・指標 |
| **`no-store`（新設）** | みんかぶ | **×** | **保存しない** | 3 タグでは表現できない。派生値を作るためメモリ上に一時存在してよいが、**永続化する型が存在しない**。`f_yutai_source_text` として物理分離し、公開 Worker に bind しない |

`no-store` が必要な根拠: `yutai_benefits.description` は 8,314 行 1,234,922 B すべてみんかぶ掲載文で、規約が蓄積そのものを禁じている。現状の保護は `publicSummary()` を通すという人間の規約に依存しており、スキーマにもテストにも強制が無い。

派生値は**入力のうち最も厳しいタグを継承する**（現行 `licensing.py` の方針を踏襲）。NamedQuery が `reads` を宣言するので、これは自動的に計算できる。

### 8.4 writer の排他

`jss_writer_claims` は 4 行あるが**照合コードが両リポジトリに 0 行**で、しかも両方が書く `core_stocks` は誰の所有でもない。マニフェストの `owner` を writer の一意宣言とし、**二重 writer を CI で検出する**。ただし D1 自体は 1 つのままなので物理分離ではなく、手動スクリプトや REST 直叩きは CI をすり抜ける（§11 に記載）。

## 10. 採らなかった選択肢と理由

### 10.1 Python 全廃 → TypeScript 単一モノレポ【採らない】

**採る理由（enhanceability 案の主張）は強い:** 二重実装が実在する（Yahoo は Python `yfinance_prices.py` ↔ TS `src/shared/yahoo`、JPX は `jpx_margin.py` ↔ `src/shared/jpx`、EDINET は `collectors/edinet.py` ↔ `scripts/sync/yuho-edinet.ts`、TDnet は `tdnet_yanoshin.py` ↔ `scripts/sync/ir-tdnet.ts`）。`universe_guards.py` は「`universe.ts` の `:82-120`、定数は `:55/:57/:59/:61` の 1:1 移植」と**行番号で手動同期を宣言**している。JPX の `.xls`→`.xlsx` 回帰テストは TS 側にしかない。同じ Yahoo 日足を 3 本のパイプラインが別時刻に取得している。

**それでも採らない理由:**

1. **規模。** Python 本体 12,534 行 + テスト 9,258 行 = 21,792 行（実測）。ロジック本体だけで collectors 2,054 + convert 740 + transform 733 = 3,527 行。個人プロジェクトで、しかも「エンハンスしやすさのために当面のエンハンスを止める」という自己矛盾を抱える。
2. **XBRL の移植リスク。** `convert/` 740 行が `lxml` 依存。名前空間・コンテキスト解決・単位・符号反転の細部が変わると**財務数値が静かに間違う** — 本設計が最も避けたい失敗形態。提案者自身が「最大の技術リスク」と認めている。しかも検証用フィクスチャは規約上コミットできないのでローカル検証にとどまる。
3. **痛みの原因は言語ではない。** 実害は「同じソースを 2 箇所が叩く」ことと「概念の定義が 8 箇所に散る」ことであって、「2 言語であること」ではない。

**代わりの決着:** **概念の定義だけを契約ファイル 1 箇所に寄せて両言語へ生成し、ソースごとに writer を 1 つに決めて重複実装を削除する**（§6.4）。EDINET/TDnet は Python、Yahoo/JPX は TypeScript。`local_store` 1,033 行は廃止、`notion` 2,535 行は投影に縮小。これで「定義 1 箇所」による利得の大半を、書き換えリスクを負わずに取る。

なお残る負債は正直に認める: **言語境界が残る限り、契約ファイルからの生成が正しいことを CI で検証し続ける必要がある。**

### 10.2 サービスごとに Worker を 7 分割【採らない】

Cloudflare 上のコストは $0（script 数は課金されない）で、1 サービスの修正で 7 サービスが同時デプロイされる現状は確かに粗い。しかし個人運用では**デプロイ 7 回・共有コードのバージョン整合 7 重**の複雑さが利得を上回る。**採るのは「公開／私用」の 2 分割**で、これはライセンス境界という明確な理由がある分割である（§8.2 第0層）。

### 10.3 銘柄詳細 7 枚を維持【採らない】

7 サービスの画面ロジックを捨てるのは割に合わないので**問いビューとしては残す**が、「7 枚の銘柄詳細ページ」は明確な重複であり、ここだけ**銘柄ハブ 1 枚に畳む**。Q10（なぜ今日この株が動いたか）は 1 枚でないと答えられない。

### 10.4 第2ソースとの常時突合【採らない】

stooq は実測で PoW チャレンジ HTML 796 バイトしか返さない。代替を探し続ける運用コストが、個人運用では得られるものを上回る。**自己整合チェック（§7.2）に置き換える** — 実際にそれで年次売上の 15.7% 異常を検出できている。ただし「一貫して間違っている」は検出できない（§11）。

### 10.5 Queues / Durable Objects / 外部監視 SaaS / IaC【採らない】

カーソル駆動化（§7.5）で cron 精度への依存が消えるため再試行基盤が要らない。外部監視は GitHub Issue + `ops_dataset_freshness` で足りる（追加 $0 vs 月 $0〜15 と、見に行く先が増える運用負荷）。IaC は wrangler 設定 3 ファイルに対して重すぎる。

### 10.6 R2 Infrequent Access への移行【採らない】

Standard $0.015/GB-mo に対し IA は $0.01/GB-mo だが **Class A $9.00/M（2倍）・Class B $0.90/M（2.5倍）・retrieval $0.01/GB・最低保存 30 日・無料枠は Standard にのみ適用**。設計書想定の 5 年後 100 GB でも差は月 **$0.41**、現実的な 34 GB では月 **$0.08**。検討すること自体が時間の無駄。

### 10.7 Notion を正本として維持【採らない】

Notion は現状 ③財務サマリ 34,551 行 / ④開示 62,115 行と D1 より豊かである。しかし (a) ユーザ向け 7 サービスが Notion を一切読まない、(b) API レートが律速で prices_daily 中央値 143.4 分のうち 60〜73 分を消費する、(c) 同じ事実が 2 系統で別々に作られ片方だけ古くなる。**正本は D1 `f_*` に置き、Notion は人が見るダイジェストへ降格。** ただし持ち直すまでの情報後退は §11 に記載。

## 11. この目標像の弱点

1. **R2 per-code は「横断 × 時系列」の問いに弱い。** 「過去 3 ヶ月で出来高が最も増えた銘柄」を素直に書くと 4,444 オブジェクトを全部読むことになる。D1 の事前計算断面で逃げるが、**新しい横断指標を思いつくたびに derive を 1 本足してバッチを回すまで見られない**。今なら SQL 1 本で試せる — ただしその「試せる」が 647,630 rows read の画面を生んだ原因でもある。エンハンスしやすさを一部犠牲にしている。

2. **公開面がほぼ空になる。** commercial-ok + factual-cite だけで作れるのは「決算が近い」「増配を発表した」「開示の時系列」程度。001/002/003/004/007 は価格も業種も personal-only 依存なので Access 配下へ移る。SEO・共有・誰かに見せるという価値はほぼ失われる。**ライセンス遵守と公開価値は本質的にトレードオフで、この案はライセンス側に倒している。**

3. **「5 年」を当面名乗れない。** EDINET 本決算の深さは平均 3.16 期、5 期以上 265 銘柄、10 期以上 1 銘柄。価格は R2 に 10 年あるが**財務側の「5 年成長」は言えない**。バックフィルには収集時間の追加投資が要る。

4. **as_of を正直に出すと体験が一時的に悪化する。** 優待 81.5 日、財務 D1 側 0 行。「古い」と書かれた値ばかりの画面になる。正直さは正しいが、**ユーザは「古いと書いてある画面」より「何も書いていない画面」を好むかもしれない**。降格表示のデザイン次第で信頼を得るか離脱を招くかが分かれる。

5. **移行直後は全ジョブが赤くなる。** 帯域チェックと SLO を有効にすると、現状の「毎日 101 銘柄失敗」「33 日凍結」「81.5 日凍結」が一斉に可視化される。**赤が多すぎると結局それも信号価値を失う**（現在の 35% 赤と同じ）。SLO を最初は緩く設定して段階的に締める運用が要るが、その「緩い SLO」が惰性で残るリスクがある。

6. **帯域チェックは正常な急変を誤って弾く。** ストップ高連続・TOB・極端な薄商い、特に**株式分割は調整係数を別途取らないと必ず引っかかる**。棄却行を `f_ingest_gaps` に残して人が見られるようにするが、これは人手コストを増やす方向で、「人手をかけずに回る」という目標と正面から衝突する。閾値の緩さと見逃しのトレードオフに正解は無い。

7. **言語境界が残る。** §10.1 の決着により Python と TypeScript が併存し、契約ファイルからの生成が正しいことを CI で検証し続ける必要がある。生成が壊れたときは両言語で同時に壊れる。

8. **D1 を共有し続けるので writer の排他は完全ではない。** マニフェストの `owner` と CI で二重 writer を検出するが、手動スクリプト・REST 直叩きは素通りする。D1 を分けると横断クエリが不可能になるため、**意図的に妥協している**。

9. **CI が本番 D1 に読み取り権限を持つ必要がある。** `rows_read ≤ 20,000` を検証するには代表クエリを実際に実行するしかない（Drizzle の動的 where は静的解析できない）。§8.5 の権限最小化と逆行する。読み取り専用トークン 1 本で妥協するが、穴は穴である。

10. **Notion 降格の過渡期に情報量が減る。** ③34,551 行・④62,115 行（2022-03 以降・EDINET 含む）は D1 側（`jss_financials` 0 行、`ir_disclosures` 37,641 行・TDnet のみ・2023-06 以降）より豊かで、持ち直すまでは**正本一本化が情報の後退として現れる**。

11. **自己整合チェックは「一貫して間違っている」を検出できない。** Yahoo が全銘柄で一律にずれた値を返し始めたら気づけない。stooq 死亡を受けた現実的な妥協であり、**正しさの上限を下げている**。

12. **通知は届いても見ない可能性がある。** 構造では解けない。週 1 回の heartbeat で緩和するが完全な解ではない。

13. **SLO の閾値はほぼ全部「実測値 + 余裕」の恣意的な数字。** 日次 30h、月次 40 日、キャッチアップ上限 20 営業日（実測最長の空振り 11 営業日の 2 倍弱）に業務上の根拠は無い。

|---|---|---|
